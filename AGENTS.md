# Workstream

Workstream gives each task its own cloud desktop with an AI agent working on it; a person watches it live, talks to the agent and takes over when they want, with up to four tasks on screen at once. It is built the way Genius (`agenetix/ChecklistSquad`) is built: SqlOS as the data model, a plain REST API, one Expo app, Bicep, and releases by GitHub release. Read [README.md](README.md) for the layout and how to run it.

Built: sign-in by emailed code (a password in development), and with GitHub beside it where a GitHub OAuth client is configured (SqlOS's own connection, seeded in code, with the `repo` scope; Workstream reads the person's GitHub token through `IGitHubTokens`); teams, invitations and administrators; environments (a repository picked from the person's GitHub repositories, surfaces (where the product runs: the browser and the phones) and applications (what the person and the agent work with), size, and the advanced settings: setup script, variables, instructions), filled from the repository's `workstream.yml` when it has one (read again at each task's start), with an example of the file shown when it has none (Workstream never guesses a setup), and saved back to the repository as `workstream.yml` by a commit or a pull request; tasks with a desktop each, started, paused, resumed and deleted; a desktop nobody is using paused after its team's time (30 minutes unless the team's administrator changes it) and archived after its team's days paused (7), where use is the agent working, a message, a person's mouse or keyboard, or a model call from the desktop by any tool, and never an open pane, and a paused or archived desktop comes back when someone clicks it or writes to its agent; the conversation between people and the agent; the live desktop in the browser through the API's relay; the workspace with up to four tasks side by side by drag and drop; sharing a task with people outside the team by email, to watch it, to write to its agent or to use its desktop too, for an hour, a day, a week or until it is taken back, with "Shared with me" in the sidebar; a spare desktop kept running for a team while someone is in its workspace, so their next task starts at once (off unless a deployment turns it on); a saved setup per environment, its repository cloned and setup script run once on a machine of its own whose disk tasks then start from; the setup script given 45 minutes unless a deployment says otherwise, shown on the task's screen while it runs on the task's own desktop and said plainly, with its last lines, when it fails or runs too long; a desktop made for a project's whole stack, where `host.docker.internal` is the desktop from its containers as it is on a Mac and the Android emulator runs on every size; an Android phone and an iPhone simulator as surfaces of an environment (`android`, `iphone`), each in a window of its own on the desktop, where the agent taps through a change the way a person would (`phone`, `desktop/agent/phone.mjs`), and hands work over with a picture of each surface in the conversation (`surfaces show`, `desktop/agent/handover.mjs`), the simulator already on a second image each release makes (`machine-iphone`), so nothing installs it when a task starts; the iPhone app built on a Mac by Workstream itself, as a workflow of its own repository that the API starts and that never writes a project's output to its public log (`.github/workflows/ios-build.yml`, `builder/ios.sh`, `api/Builds/`), kept one a team for each hash of the app's native code, with the Mac's minutes in the team's usage; an email to the people of a task when its agent finishes or asks a question, with a switch to turn it off; a desktop resumed after a pause, or brought back from its archive, bringing back the commands, pages and files it had; usage and limits per team; the system administrator's page with the running-desktops curve, what the desktops cost and how long they take to start; the model gateway to Foundry with a monthly allowance per team, every call saved with the person it counts to and the tool that made it and never its words; a desktop opened with nothing asked of its agent, for a person to work on ("Open desktop", a task with no prompt), with a terminal that says what is ready; OpenCode on every desktop at a pinned version, pointed at the team's models with no sign-in and no key through the desktop's own model address (`desktop/agent/model.mjs`, `desktop/agent/opencode.mjs`); the Usage page's report of who and what used the models, by day, person, tool, model and task, the whole team's for an administrator (`TEAM_VIEW_PEOPLE_USAGE`) and one's own for anyone else, and the same sums over every team on the system administrator's page; a task's desktop pushing branches and opening pull requests as the person who started the task, with their GitHub token; the command line (`cli/`), signed in through the browser with SqlOS's device flow, which starts and reads tasks as the person, and the `start-workstream-task` skill that hands a GitHub issue to it; public docs pages at `/docs`, written as MDX in `client/content/docs`. Not built: payments, sign in with ChatGPT, pull-request previews, a phone app, a custom domain.

## The rules

1. **Model on SqlOS first.** [docs/core-model.md](docs/core-model.md) defines the system: principals, nodes, permissions, roles and grants. A feature that changes who, where or what may be done changes that document in the same PR. If you are about to add a column, flag, join or table that relates a principal to a node, stop: it is a grant, and its list is a page (`ToPageAsync`). When SqlOS seems to lack something, read its docs and source before concluding, then raise it; never work around it.
2. **Build the house way.** REST handlers resolve the caller, load the row and its real parent, check SqlOS on the target node (creates check the parent), call the domain and save. The verbs live once, in `api/Operations/`; the handlers in `api/WorkstreamApi*.cs` are adapters. Behavior and its rules live in `api/Domain/`. SchemaSync, no migrations. Identity side effects (a new person's team, a membership's group) happen inside the save, in `api/IdentityProvisioning.cs`.
3. **One view per surface.** A screen in `client/src/` is a folder: `props.ts` (the contract), `parts.tsx`, one file per surface (`web-desktop.tsx`, `web-phone.tsx`) and `index.ts`, which picks. Controllers live in `client/app/` and never know the surface. Views take props only. A window or platform check anywhere but `client/lib/surface.ts` is raised, not written.
4. **Every word is a key.** User-facing text lives in `client/locales/<namespace>/en.json` and is read with `useT`. The one exception is the text of the public docs pages (`/docs`), which is `client/content/docs/<page>/en.mdx`, one folder a page; the frame around it is the `docs` namespace. The system administrator's page is English only and writes its words in place.
5. **Colors come from the palette.** `client/components/theme/palette.ts` is the one list, light and dark, checked for contrast by test. Views use the Tailwind classes it backs; `useTheme().colors` is for color props only.
6. **Gates.** `cd client && npm run check`; `cd desktop/agent && npm test`; `node --test cli/*.test.mjs`; `dotnet test tests/Workstream.Tests`. Every endpoint ships allow and deny journeys per kind of caller: a team's administrator, a member, a stranger, the system administrator, a desktop with its key, and nobody.
7. **A desktop is untrusted.** It runs whatever its agent is asked to. It holds one key that reaches its own task and nothing else; it never holds a model key, a person's Workstream token or anything of another team's. With that key it may also ask for the GitHub token of the person who started its task, which is never written to its disk (`docs/core-model.md`, "A desktop's GitHub token"); that is the one person's token a desktop holds. Its key comes from its user data and is never written to its disk. It has no public address and cannot reach another desktop. Anything that would give a desktop more than that is raised first.
8. **Production ships only by GitHub release.** `vX.Y.Z` is the version in `client/app.json`. Merging to `main` deploys nothing. To try a change on Azure first, deploy it to staging (`gh workflow run staging.yml`, with `-f desktop-image=true` for a change under `desktop/`), which signs in with a password, and remove staging afterwards. Infrastructure is `infra/` and the workflows, nothing made by hand, with two exceptions that are written down: the Foundry resource and its model deployments (`infra/README.md`, "Models"), and the GitHub OAuth client people sign in with (`infra/README.md`, "Sign in with GitHub").
9. **Working with a person.** Never commit or push during synchronous work unless the person explicitly approves that commit.
